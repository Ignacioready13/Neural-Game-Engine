2. WHAT WE KNOW AND WHAT WE SUSPECT
--------------------------------------------------------------------------------
2.1 The evaluation path may not match the live path (investigate FIRST)
  - The Stage 6 report measured, on identical clicks through the live player, the mean
    frame-to-frame change (grey levels): flow96 5.98, flow96c 24.42, flow96d 14.92. So in
    the player flow96c changes about 4x MORE than flow96, consistent with "static".
  - The Stage 5b scorecard reported the opposite order for what should be the same
    quantity ("frame change": flow96 0.0048, flow96c 0.0024, real 0.022, i.e. flow96c
    smoother than flow96). Both cannot describe the same behavior.
  - The player samples frame f with noise seed (noise_seed + f), i.e. FRESH noise every
    frame. Suspicions to check in code and with a short run: the scorecard/old GIF
    rollouts used a fixed noise tensor per rollout or per step (which gives smooth, frozen,
    deterministic output, like pillars morphing in place); the Stage 5-era player had the
    bugs listed in the Stage 6 report (§0 rows 2-4: repeated action instead of real
    history, unbounded history, debounce state); different seed contexts or sampler
    settings. The 5b "winner" was selected by a path that may not reflect live play.
  - Consequence: from now on EVERY rollout used to make a decision must come from the
    live player's own code path (Player.generate, headless mode), with fresh noise per
    frame, from real seed contexts, in a no-click scenario and a real-click scenario.

2.2 What the GameNGen paper contributes (read the cited sections if useful)
  - Sec 3.2.1, Fig 4, Fig 7, Sec 5.2.2: autoregressive generation drifts and collapses
    after 20-30 steps even when the player does not move (their Fig 4 is exactly our
    no-click failure). Their fix, called noise augmentation and described as critical:
    during training, corrupt the CONTEXT frames with Gaussian noise of a random level
    drawn uniformly up to a maximum (0.7 in their latent units), discretized into 10
    buckets, and give the model the level through a learned embedding, while the TARGET
    stays the clean next frame. The model learns to correct imperfect past frames. At
    inference the added level is controllable (even zero already works much better).
    Without it, quality degrades within 10-20 steps; with it, it holds over 64+.
    Stage 5 used only a small FIXED noise (about 0.05) with no level conditioning, which
    is very different.
  - Sec 3.3: classifier-free guidance applied ONLY to the frame context, weight about 1.5
    (larger weights add artifacts that grow in autoregressive use); the context is
    dropped with probability 0.1 in training to allow this. 4 sampling steps are enough
    (no quality loss versus 20+).
  - Sec 5.2.1 / Table 2: more context frames barely help (4 vs 64 frames: almost the
    same). So do NOT spend effort on longer context or memory.
  - Appendix A.3, Fig 13: they overfit small datasets quickly (with 1M examples,
    test PSNR peaked near 20k steps at batch 128 then FELL; larger datasets peak later).
    Our train set has about 0.65 M windows that are highly redundant, and 6.5 hours at
    ~10 steps/s and batch 48 is about 11 M samples (15+ epochs). Do not assume longer is
    always better: track validation and the live-path health numbers over time, keep
    snapshots, and select by health, not by the last step.
  - Sec 4.2: constant learning rate 2e-5, batch 128, gradient clipping 1.0, no weight
    decay. They are trained teacher-forced only (no self-rollout in training).
  - Sec 5.1: per-frame metrics against ground truth stop being informative after a few
    autoregressive steps (trajectories legitimately diverge); they used human raters.
    That matches our situation: the user's eyes are the judge, and our numbers are only
    collapse detectors.
2.3 Lessons already paid for
  - flow96d had better validation loss, better one-step scores and a better reveal ratio,
    and was worse where it counts. Neither validation loss nor one-step scores can select
    models here. Selection must come from long live-path rollouts.
  - The 5b "opening share" detector (precision 0.61) was satisfied by dark holes next to
    yellow slabs. Do not use it. The user's eye said flow96c is incoherent.
  - The old vertical structure of failure: the generator is not anchored to the structure
    it was just given, and each frame injects fresh high-frequency noise; per-step effects
    that are tiny (turns, door growth) get swamped. Noise-level-conditioned context
    corruption is the published remedy for the drift part.

4.1 Phase 1: pilot gate (one pilot, one fallback; each about 25 minutes of training)
 The recipe to test (call it the GameNGen-style recipe), a NEW run named flow96e_pilot:
   - Same architecture and data as flow96c (3.19 M denoiser with low-res attention),
     same frozen steering core, same step count (12,000) and batch, so the comparison with
     flow96c is fair.
   - Noise-level-conditioned context corruption as in GameNGen Sec 3.2.1: every frame-valued
     conditioning input the generator sees (the context frames and the warped last frame)
     is corrupted with Gaussian noise whose level is drawn per sample, uniformly from 0 up
     to a maximum, discretized into about 10 buckets, and the bucket is given to the model
     through a learned embedding. Start with a maximum of about 0.5 in the [-1, 1] pixel
     scale (about one data standard deviation), with 20-30% of samples left clean. The
     TARGET is the clean next frame. IMPORTANT pitfall: the model must not see a clean
     answer through the corrupted input. Our generator predicts a residual relative to the
     warped last frame; define the base the model actually sees (the corrupted warped frame)
     and the target relative to the CLEAN truth, so the model has to learn to remove the
     noise, not copy it. At inference use level 0 (the player must do this automatically;
     older models must keep working bit-identically).
   - Context dropout with probability 0.1 (a learned null conditioning), so that guidance
     can be tried at inference (4.3). Keep the 4-step sampler.
   - EMA of the weights (decay about 0.999 to 0.9995; use the EMA weights for all
     evaluation and for the player), gradient clipping 1.0.
   - Keep the self-rollout curriculum exactly as flow96c had it (self_k 4, p 0.25); do not
     lengthen it (roll-in cost is large). Use fresh noise in any roll-in.
   - Mirror augmentation if the existing training code already supports it; otherwise leave
     the data handling alone.
 GATE (use the live path, no-click, fresh noise, 3 seed contexts, 300 steps, EMA weights):
   PASS = the health numbers of 4.0d are inside the pass band in at least 2 of 3 contexts
   at step 300, AND (if the judge was accepted) the judge rates at least 70% of the frames
   at steps 100+ as corridor-like. Compare with flow96 and flow96c in the same table.
   If the pilot passes: the main run uses this recipe (4.2).
   If it fails: run ONE fallback pilot, flow96e_pilot_small: the same recipe on the SMALL
   denoiser size of flow96 (0.77 M, no attention), 12,000 steps, same gate. If it passes,
   the main run uses the small architecture. If BOTH fail, the main run uses whichever was
   healthier, with the corruption maximum raised (for example to about 0.7) and a clear
   note in the report. Pilots must be finished by T0 + 2 h 15 min at the latest; if they
   are running late, stop them and launch the main run anyway with the better one so far.
 Do not train anything else in the pilot phase (no other variants, no sweeps).
