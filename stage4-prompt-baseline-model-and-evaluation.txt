1. PURPOSE AND CONTEXT
--------------------------------------------------------------------------------
The project's end goal is a neural network that acts as a game engine: given a few
recent frames and the player's click signal, it generates the next frame, over and
over, in real time (15+ frames per second on this laptop's RTX 5070 with 8 GB of
VRAM), producing an endless backrooms-style maze of hallways and rooms that never
existed in advance. The class this is for also asks what the system's algorithms
are and what hardware suits them, so measurements of the model (size, compute,
latency, memory) are valuable too.

Why a baseline first. The likely final model is an action-conditioned diffusion
model. That is a lot of machinery. Before building it we want to know, cheaply:
  (a) that the data, labels, loader and training loop are correct end to end;
  (b) that the action signal really carries information the model can use, and that
      the alignment rule (action[i] drives frame i to frame i+1) is right in
      practice and not just on paper;
  (c) what a simple, deterministic next-frame predictor can and cannot do. The
      expected failure is that, when something new is revealed (a room beyond a
      doorway, the content of an unseen corridor), a model trained to minimize pixel
      error predicts a blurry average, because the true next frame is one of many
      possibilities. That blur is precisely the argument for a generative (diffusion)
      model, and we want it documented with evidence;
  (d) the evaluation tools we will keep using.
This stage is NOT trying to produce a good-looking generator.

Data facts you need (details are in the Stage 3 report):
  - Pilot: about 88,000 frames; train 119 episodes (about 70,600 frames), val 15,
    test 15. 20 Hz. Packed at 96x72 and 64x48. Frames within one episode are highly
    redundant (consecutive frames are nearly identical).
  - Each action is a float vector [actionX, actionHasClicked]; actionX in [-1, 1] is
    the held click position (a horizontal screen position, resolved by the engine to
    the nearest reachable door), 0 with hasClicked = 0 before the first click.
  - The loader already drops windows containing viewUnsafe frames by default; keep
    that default for training and evaluation.
  - The analysis sidecar carries ground-truth quantities that are NOT model inputs but
    are useful for evaluation: player pose and heading, angular velocity, which doors
    were visible and reachable with their screen positions, the persona, and so on.
  - Most frames are steady forward walking; the action matters mainly around turns and
    choices, so overall averages can hide whether the model uses the action.

2. WHAT TO BUILD
--------------------------------------------------------------------------------

2.1 The baseline model
  A small, deterministic, action-conditioned next-frame predictor: K context frames
  plus the K corresponding actions in, one predicted next frame out, trained with a
  plain pixel loss. Architecture, K (start around 4), loss details, and how the
  action is injected are your decisions; document them. Guidance rather than orders:
    - Keep it small. This is a baseline and also the starting point for a real-time
      budget; it should be able to run far faster than 15 frames per second.
    - The action is a horizontal screen position whose effect depends on where doors
      are in the image, so the way it is injected may matter (for example conditioning
      at more than one scale, or as extra image-shaped input). Try the simplest option
      first. If the action ablation of 2.4 shows the model ignores the action, try
      ONE alternative conditioning scheme before concluding anything.
    - Predicting the change from the last context frame (a residual) rather than the
      whole frame is a common, useful choice when consecutive frames are so similar.
    - Mixed precision is fine. Do not rely on torch.compile; use it only if it works
      without effort.

2.2 Training setup
  Develop and iterate at 64x48 (fast), then run the same recipe once at 96x72 and
  report both. Select the checkpoint and any settings on the validation split only;
  touch the test split once, at the end, for the final reported numbers. Seed
  everything, save the configuration and results of each run, save checkpoints and
  loss curves under a gitignored location, and keep the code able to train from a
  config so later models can reuse it. Report the train/validation gap (the pilot is
  small, so overfitting is possible).

2.3 Reference predictors
  Evaluate, on the same windows as the model: (a) "persistence" (repeat the last
  context frame), which is the number to beat; and (b) optionally a cheap
  constant-motion extrapolation if you can build one quickly. A model that cannot beat
  persistence has not learned anything useful.

2.4 The evaluation harness (the long-lived part)
  Build it so it can evaluate ANY future model that has the same interface (context
  frames and actions in, next frame out, plus an autoregressive rollout driver).
  (a) One-step (teacher-forced) metrics on val/test windows: simple, standard pixel
      metrics (for example L1 or MSE, PSNR, SSIM; implement lightweight versions
      rather than adding heavy dependencies), reported overall AND on an
      "action-relevant" subset that you define from the sidecar (for example windows
      where the true heading changes noticeably in the target step, or where the action
      changed in the last few frames). Document the definition and the subset size.
  (b) Alignment and action-use ablation, WITHOUT retraining: evaluate the trained
      model on the same windows with (i) the true actions, (ii) actions zeroed,
      (iii) actions shuffled across windows, and (iv) actions shifted by one frame
      earlier and by one frame later. If the schema's alignment rule is right in
      practice and the model uses the action, the true alignment should score best,
      especially on the action-relevant subset. Report the numbers. This is an
      empirical test of the Stage 2 off-by-one fix; the outcome matters (see check-in
      trigger (ii)).
  (c) Rollouts: starting from real context, generate N steps (try about 40) feeding the
      model its own predictions while supplying the TRUE action sequence from the clip.
      Report error versus horizon for the model and for persistence, on a sample of val
      clips (for example 30 to 50), and note when the model stops being better than
      persistence.
  (d) Action-following. We want a measurable answer to "does clicking toward a door
      turn the view toward it?" Design a simple quantitative metric, for example:
      estimate the horizontal image shift between successive frames (a basic
      shift-search or phase-correlation estimate is enough), and compare the shift the
      model's predicted frames show against the shift in the real frames (and against
      the sidecar's ground-truth heading change). Report the agreement for the model,
      for persistence, and for the zeroed-action ablation.
  (e) Counterfactual direction test. Take val contexts in which at least two doors are
      reachable on opposite sides of screen center (from the sidecar's candidates). Roll
      the model forward a short distance (about 10 to 20 steps), holding as the action
      the screen position of one door, then of the other, then no click. Report the share
      of contexts where the predicted view turns toward the door that was clicked (the
      scene content moves the opposite way in the image). Because the engine is
      deterministic and path-dependent we cannot get ground-truth counterfactuals from
      the pilot itself, so this tests direction, not exact pixels.

2.5 Learning curve (do this if each run is cheap enough; otherwise do two points)
  Train with 10%, 30% and 100% of the training windows (same recipe, fixed time or step
  budget per run, documented) and report validation metrics against data size. If a run
  is too slow, use only the 30% and 100% points. This tells the user how much bulk data
  to generate, so state what the curve suggests (still improving steeply, or flattening).

2.6 Speed and resource measurements (for the project's hardware discussion)
  Report: parameter count; approximate multiply-adds (or FLOPs) per generated frame;
  numeric precision used; peak GPU memory in training and in inference; and inference
  speed on this GPU at batch size 1 (frames per second for one frame at a time, which
  is what real-time play needs) and for the autoregressive rollout loop including any
  overhead. Say how close this is to the 15 fps target and what that implies for a
  model that needs several denoising steps per frame.

--------------------------------------------------------------------------------
3. WHAT TO EXPECT AND WHAT TO LOOK OUT FOR
--------------------------------------------------------------------------------
  - Steady forward motion is easy; turns, doorway reveals and new rooms are hard. A
    good baseline will beat persistence mainly on the first.
  - Blurry predictions where new content appears are expected and are a finding, not
    a bug. Report where the blur shows up.
  - Rollouts will degrade as errors compound; the point is to measure how fast and in
    what way (blurring, geometry melting, color drift), not to fix it here.
  - Do not "fix" poor results by changing the labels or the data. If the numbers look
    wrong, trigger a check-in.
  - Overall metrics can look good while the model ignores the action. That is why
    2.4(b), (d) and (e) exist.

Produce exactly three images in a gitignored review folder, using the best model at

When you finish, tell the user the paths and what to look for: (1) the prediction should
resemble the true next frame, blurrier but not nonsense, and visibly closer than
persistence during turns; (2) rollouts should stay recognizable for a while and then
degrade, and the user should note how; (3) the left-click and right-click rows should
visibly turn in different directions. Keep the images small enough to view comfortably
(enlarge with nearest-neighbor).

5. ACCEPTANCE CHECKS (this is the whole list; do not add to it)
--------------------------------------------------------------------------------
 1. Sanity overfit: the model drives its loss near zero on a tiny subset (for example a
    few dozen windows) within a couple of minutes, proving the model, loss and training
    loop can learn.
 2. Beats the reference: on the val split, the trained model beats persistence overall;
    report the numbers for both resolutions.
 3. Alignment/action ablation (2.4(b)): report true vs zeroed vs shuffled vs shifted
    actions, overall and on the action-relevant subset.
 4. Rollout error versus horizon (2.4(c)) for the model and persistence.
 5. Action-following and counterfactual-direction results (2.4(d), (e)).
 6. Speed and resource numbers (2.6).
 7. Test split evaluated once at the end with the final model; report it.
 8. The existing tests from Stage 3 still pass; add a few small tests for the new
    evaluation code (for example the metric functions and the action-shift
    transformations) but do not write an exhaustive suite.
Everything visual is judged by the user. Not requested, so do not do them: sweeps over
many hyperparameters, other model families, diffusion or generative models, a
real-time client, bulk data generation, anything in /engine.
