SECTION 1 — THE CONTROL SIGNAL AND CLICK SEMANTICS
--------------------------------------------------------------------------------
This is the most important section. The trained network will be conditioned on
one per-frame value, called controlSignalX in the manifest. I need to know
exactly what it means.

1.1 [P1] Trace one click end to end. Starting from the pointer/mouse event in
    human mode and from the bot/scripted-input path in headless mode, list every
    function the click passes through until it changes simulation state, and
    what state it changes. Is the interaction "click once to set a target" or is
    any hold/drag behavior involved? Is mousedown, mouseup, or click used?

1.2 [P1] What exactly is stored in controlSignalX each frame? Is it (a) the raw
    X of the most recent click, (b) the X of the most recent ACCEPTED click (i.e.
    not discarded by debounce), (c) something derived from the chosen doorway,
    or (d) something else? Give the code that sets it.

1.3 [P1] Debounce: when a click arrives inside the debounce window, what
    happens to (i) the steering target, (ii) controlSignalX, (iii) the click-pulse
    visual? Are ignored clicks recorded anywhere in the manifest?

1.4 [P1] Between clicks, is the steering target STICKY (a specific doorway is
    chosen and kept until passed) or is the target RE-RESOLVED EVERY FRAME from
    the held X? If it is sticky, what are the exact rules for when the sticky
    target is cleared or replaced (door passed, door leaves the candidate set,
    door becomes unreachable, entity disposed, etc.)?

1.5 [P1] When the player passes through a doorway into a NEW entity (hallway,
    room, junction, bend), what happens to the previous click? Specifically:
    does the held X still influence steering in the new entity, does it reset to
    the screen-center default, or something else? Does controlSignalX in the
    manifest change at that moment? If the logged signal and the engine's actual
    steering behavior can disagree at any point, describe every such case.

1.6 [P1] Default behavior: when there is no active click, which doorway is
    targeted and by what rule (nearest to screen center? straightest in world
    heading?). Is this rule evaluated per frame or only when a new entity is
    entered?

1.7 [P1] Coordinate convention: how is a click's pixel X converted to the
    normalized value? Is it relative to canvas width, centered, and range -1..1?
    Which sign is left? Is the mapping linear in screen pixels or in view angle?
    Does supersampling (RENDER_SCALE), CSS scaling, or aspect ratio affect it?
    How is each doorway's on-screen X computed (same camera, same FOV, same
    projection)? Cite the code for both.

1.8 [P1] What is the range and typical resolution of the signal in practice?
    Can it take the exact values -1 and +1, and can it be exactly 0 after a real
    click (as distinct from the "no click yet" default)? Is there any way for
    the manifest to distinguish "never clicked" from "clicked dead center"?

1.9 [P2] Are clicks ever ignored for other reasons (during a gated turn phase,
    while no candidates are reachable, during entity transitions)? List them.

1.10 [P2] Is there any other input besides click X (keyboard, scroll, Y
     coordinate)? Confirm nothing else affects the simulation.

SECTION 2 — FRAME / SIGNAL TIMING ALIGNMENT
--------------------------------------------------------------------------------
For an action-conditioned model I must know which signal value CAUSES the
change from frame i to frame i+1.

2.1 [P1] Write out the exact per-frame order of operations in BOTH the headless
    loop and the human recording loop: when is input read, when is the click
    processed, when is the simulation stepped, when is the frame rendered,
    when is the image captured, and when is controlSignalX sampled and logged?

2.2 [P1] Given that order: if a click arrives "during" frame i, does it
    first affect the image of frame i, frame i+1, or later? Which manifest
    index records the new signal value first? State plainly: "the transition
    from frame i to frame i+1 is driven by controlSignalX[__]" (fill in the
    index relationship) and prove it with a tiny scripted test: inject a single
    click at a known frame and show the first frame index at which (a) the
    logged signal changes and (b) the player heading begins to change.

2.3 [P1] RUN: measure click-to-motion latency. For clicks on doors at several
    distances/angles, report frames from click until heading changes by more
    than 1 degree, and frames until the player is aligned with the target. Give
    min / median / max, and note how it varies with jerk limiting and turn gating.

2.4 [P2] Are there duplicated or skipped frames (e.g. frame 0 handling, last
    frame handling, frames where the render did not update)? Is
    simulatedTime exactly frameIndex * timestep for every frame?
