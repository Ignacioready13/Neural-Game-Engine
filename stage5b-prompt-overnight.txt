1. WHAT WE LEARNED AT CHECK-IN 1 (USER'S PLAYTEST AND THE REVIEW IMAGES)
--------------------------------------------------------------------------------
  - Steering works: clicks clearly turn the view. No engine-side steering change is
    wanted. Do not pursue one.
  - But in long closed-loop play NO DISCRETE DOORWAY EVER APPEARS. Side walls morph into
    blurry smears, the far end of the hallway is a black void, the floor and ceiling grow
    glossy blobs, and the no-click run sinks into a dark tunnel. It feels like one long
    endless hallway. The user (who judged by eye) says this is the gap.
  - Your gates passed but do not capture this: mean-gradient "sharpness" can be satisfied
    by grain; reveal-moment seed diversity was only 1.09x steady walking; one-step L1 is
    about 4x the baseline's. The generator does not yet invent structure.
  - A faint red-brown tint is visible at the bottom of dark regions in the long-run
    images; check colour statistics inside dark regions.
  - The dark/black areas in the real data are NOT always doorways: the game uses heavy
    black fog and some very large rooms whose far walls and doors vanish into black.
  - Likely causes to test (not assumed): (1) the structured motion is translation-only,
    but walking forward makes the walls and doorways expand outward every frame, which the
    generator must then invent; (2) the generator (about 0.77M parameters for the denoiser,
    17 minutes of training) is small and undertrained, while real-time has a 4.5x margin;
    (3) long-horizon exposure bias; (4) the readout loses information on generated frames.

3. POWER AND ENERGY ACCOUNTING (THE USER'S CLASS NEEDS THIS)
--------------------------------------------------------------------------------
Goal: watt-hours (Wh) for every training and evaluation run from this point on, the
Wh for the winning model's training, the total Wh for everything done from now, and the

3.1 FIRST 15 MINUTES — tooling check (the only user-dependent step)
  Determine what power telemetry this laptop offers WITHOUT sudo, in this order:
   (a) NVIDIA GPU power via NVML/nvidia-smi (power.draw, plus temperature, clocks,
       throttle reasons). Confirm it returns a real number, not [N/A].
   (b) CPU package/DRAM power via Intel RAPL (/sys/class/powercap/intel-rapl*/energy_uj).
       Recent kernels make these root-readable only; check whether they are readable.
   (c) Battery/AC counters under /sys/class/power_supply (usually only meaningful when
       discharging; do NOT ask the user to unplug the laptop).
   (d) Any installed monitoring tool you already know of.
  Pick the simplest sufficient set. GPU power alone is already useful; GPU + CPU package
  is better; whole-wall power is not available on mains and that limitation must be
  stated in the report (screen, fans, SSD and RAM are not captured).
  If something useful needs sudo or an installed program (for example making the RAPL
  files readable, or installing a monitoring tool), do NOT run it. Send ONE plain-text
  message right away, beginning "SUDO NOTE (no reply needed)", containing the exact
  command(s) the user could run, what each does, and that it is optional. Then CONTINUE
  immediately with GPU-only logging; the logger must re-check CPU/RAPL readability at the
  start of every run so that if the user runs the command later (for example in the

  reply. If you need nothing, say so in one line ("Power tooling: nvidia-smi only, no
  action needed from you") so the user can go to bed knowing.

3.2 The logger
  A small reusable tool (pip-installable inside the venv only, e.g. nvidia-ml-py, if you
  need it) that samples power at about 1 Hz in a background thread, integrates to Wh
  (trapezoid rule), and wraps any job: a context manager or a wrapper script that composes

  running) and report both gross energy and idle-subtracted ("net") energy.
  Ledger totals: (i) everything since this phase began (training and evaluations);
  (ii) the training energy of the winning model's lineage, i.e. all runs that contributed
  to the final checkpoint through parent_run links (state exactly which runs). The user
  will report (i) and (ii) separately.
  Earlier Stage 5 runs (about 4.5 GPU hours, before this logger existed) were not
  measured. In the report give a clearly labelled ESTIMATE: their recorded durations

4. BUILD THE FROZEN SCORECARD FIRST (BEFORE ANY NEW TRAINING)
--------------------------------------------------------------------------------
You are not able to see, and your self-assessment of generated frames is unreliable.
Therefore define, implement, validate and FREEZE a scorecard before you change the model,
score the current model (the incumbent "v0" = flow96 on steer96) on it, and judge every
candidate only against it.

4.1 Frozen evaluation sets (save to neural/eval_sets/scorecard_v1.json; never change them)
  - 40 val clips (distinct episodes, mid-episode) for 300-frame closed-loop rollouts in
    three scenarios: no clicks, the clip's real clicks, and a scripted alternating
    left/right pattern; plus fixed sampling seeds (3 seeds per rollout).
  - The steering contexts from Gate G1 (at least 300 near-door two-door contexts).
  - A second, disjoint "confirmation" set of 40 val clips, used ONLY once at the end to
    confirm the final pick (so that you do not overfit the main set).
  - The test split is used once, at the very end, as before.

4.2 Scorecard metrics. All are computed identically for every candidate.
  S. Steering (must not regress): the G1 numbers (near-door both-directions counterfactual,
     per-side, shift ratio at H = 10, sustained ratio and sign in 8-step blocks, commanded
     and measured), with and without the generator in the loop.
  R. Realness / spectrum (grain cannot game these):
     - radially averaged power-spectrum distance between generated and real frames, and
       per-frequency-band ratios (a blurry model is low at high frequencies; a grainy one
       is high; both are visible) at horizons 20, 60, 150 and 300;
     - Laplacian-variance ratio and a multi-scale gradient statistic, per horizon;
     - a real-versus-generated CLASSIFIER TWO-SAMPLE TEST: train a fresh small CNN
       per candidate to tell real frames from generated frames (train it on rollouts from
       one set of clips/seeds and test on held-out clips/seeds); report held-out AUC at each
       horizon (0.5 is ideal, 1.0 means trivially distinguishable). Caution: it can latch
       onto grain; use it alongside the spectrum, never alone.
  D. Structure / doorways (the user's actual complaint):
     - Build a FROZEN "opening detector": a small CNN trained once on REAL train frames,
       with labels derived from the sidecar (decide from the sidecar's door candidates
       what "a doorway or side opening is visible in the frame" means). Validate it on
       real val frames (precision/recall) and include NEGATIVE CONTROLS: real frames that
       are mostly black fog or large dark rooms WITHOUT a visible doorway must not be
       detected as doorways. If precision on those controls is poor, say so and fix or
       discard the detector. Never retrain this detector on generated frames.
     - For real clips and for generated rollouts report: detector-positive frame share,
       and "opening events" (an opening appears, moves by, and leaves) per 100 frames, at
       each horizon, real versus generated.
     - Also, at real doorway-reveal moments (windows where a new opening enters view in the
       next frames, from the sidecar), compare the generated region with real and with the
       Stage 4 baseline, and report the detector-positive rate on generated one-step
       outputs.
  H. Long-run health: per-channel colour means and the colour statistics INSIDE DARK
     REGIONS (the faint red-brown tint), mean luminance drift, near-black and near-white
     shares, frame-to-frame change, measured motion (px/step) versus real, a "frozen
     image" check; all by horizon, per scenario.
  T. Speed: the G4 loop at batch 1 (must stay at least 25 fps; hard floor 15) and VRAM.
  Make noise visible: evaluate the incumbent with 3 sampling seeds and record the
  seed-to-seed standard deviation of every metric; a "real" improvement must exceed noise.

4.3 Validate the judges before trusting them (about 30 minutes, GPU-light)
  Show that each judge can tell things apart that you know are different: real frames vs
  real frames with added grain; real vs blurred real; real vs the Stage 4 baseline's
  melted rollouts; the current generator's 300-step frames vs real. A judge that cannot
  separate known-different cases is not used.

4.4 Score the incumbent v0 on the full scorecard and save the results. This is the
    reference every candidate must beat.

5. DIAGNOSE, THEN ITERATE
--------------------------------------------------------------------------------
5.1 Diagnosis (at most 45 minutes, mostly evaluation; put numbers in the progress file):
  1. Forward motion: measure how much of the real frame-to-frame change is forward-motion
     expansion (zoom/radial flow about the vanishing point) versus horizontal shift (fit
     zoom + shift between consecutive real frames; compare residual error against the
     translation-only warp).
  2. Reveals: how often does the incumbent generator produce a door-like opening in newly
     revealed regions, compared with real (use the frozen detector).
  3. Under-training/capacity: was validation loss still falling when the core and the
     generator stopped? Receptive field of the denoiser versus frame size.
  4. Hardware use: samples per second, batch size, share of step time waiting on data,
     launch-bound versus compute-bound; try a larger batch and report. The user noticed
     RAM stays about half used; say whether the memory cap or the loader ever limited
     speed.

5.2 Iteration plan. Each iteration = a change, a training run (at most 90 minutes), a full
    scorecard evaluation, and a keep/revert decision under Section 6. Do them in this
    order, skipping or reordering only if the diagnosis says to, and record why. Develop at
    64x48 only if it saves real time; the final candidates must be 96x72.
  I1. FORWARD MOTION (if 5.1-1 supports it): extend the structured motion path so the
      readout also predicts a zoom/low-resolution flow (supervised in training only, from
      measured flow or the sidecar), and the warp applies it, so the generator is left to
      create genuinely new content (new openings, revealed surfaces) rather than to
      reinvent expansion every frame. Retrain the core, then the generator on it.
  I2. SCALE AND TRAIN LONGER: a denoiser several times larger (more channels, a larger
      receptive field or low-resolution self-attention), more sampling steps if affordable,
      longer training, and a longer self-rollout curriculum (train on its own outputs over
      8-16 step roll-ins, with noise augmentation) for long-horizon stability. Stay at or
      above 25 fps. If the larger model is slower but clearly better, keep both and report.
  I3. STACK-LEVEL READOUT FINE-TUNE: fine-tune the readout on the generator's own frames
      (DAgger at the stack level) for sustained steering, only if S shows a gap.
  I4. If time remains, address whichever scorecard family is weakest for the incumbent
      (for example colour in dark regions, drift, or opening rate), with one targeted change.
  Anything that changes the training distribution or the data sampler must be recorded;
  mirror augmentation and onset oversampling remain.

6. THE KEEP / REVERT RULE (DECIDED NOW, NOT AFTER SEEING RESULTS)
--------------------------------------------------------------------------------
A candidate replaces the incumbent only if ALL of the following hold on the main frozen
set (seed-averaged, each comparison judged against the incumbent's measured seed-to-seed
noise):
  - STEERING: near-door both-directions counterfactual drops by no more than 0.03 from the
    incumbent's, shift ratio at H = 10 stays at least 0.5, sustained metrics do not get
    worse beyond noise.
  - SPEED: still at least 25 fps (or the clearly-better-but-slower case is kept separately
    and labelled).
  - HEALTH: no collapse (no scenario goes to black, white or uniform; no frozen image) and
    colour and luminance drift are not worse beyond noise.
  - IMPROVEMENT: at least two of the three families R (spectrum / classifier AUC),
    D (opening-event rate and detector-positive rate closer to real), and H (drift and
    motion fading) improve beyond noise at the 150-step and 300-step horizons, with none
    of the three getting meaningfully worse.
If a candidate wins, it becomes the incumbent. If not, revert (but KEEP its checkpoint and
its scorecard row). Do not tune the thresholds after seeing results. Training loss, L1 or a
single favourable metric is not evidence. If two candidates are close, prefer the simpler or
faster one. After the final candidate is chosen, run it ONCE on the confirmation set and
ONCE on the test split; if it regresses badly on the confirmation set relative to the main
set (a sign of overfitting to the scorecard), revert to the previous incumbent and say so
prominently.
Keep a table in the progress file: one row per candidate, all scorecard numbers, decision.
