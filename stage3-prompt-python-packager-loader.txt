1. WHERE THIS FITS
--------------------------------------------------------------------------------
The engine generates episodes: sequences of rendered frames (PNG, 320x240, 20 Hz)
plus per-frame labels. The labels that matter for training are, per frame:
  - actionX: the steering signal in effect for the step from this frame to the NEXT
    frame (a held click position in [-1, 1]); null on an episode's final frame.
  - actionHasClicked: whether the player has clicked yet (false means the engine is
    in its default "never clicked" mode; actionX is then 0).
  - viewUnsafe: a label-only flag marking frames whose view may be visually
    compromised (camera nearly touching or behind a wall). Any training window that
    contains an unsafe frame must be dropped.
Other fields (persona, raw clicks, player pose, candidate doors, and so on) are
debug/analysis information, not model inputs; carry them along in a way that later
evaluation can use but the training loader ignores by default.

The future model is an action-conditioned next-frame predictor (probably a
diffusion model working at low resolution, maybe 96x72 or 64x48). Given K recent
frames and the action for each, it predicts the next frame, and later it will be
rolled out autoregressively for many steps. The target is real-time play at 15+
frames/s on this machine's laptop RTX 5070 (8 GB VRAM). So the loader has to
support (a) ordinary training windows, (b) longer contiguous clips for rollout
evaluation, and (c) random access by (episode, frame).

The pilot (engine/data/pilot_v1/) has 150 planned episodes split by directory into
train / val / test, about 88,000 frames. A much bigger dataset (hundreds of
thousands to a couple of million frames, tens of GB of PNGs) will be generated
later with the same schema and must go through the same packager, so build for
that scale now.

2. ENVIRONMENT
--------------------------------------------------------------------------------
Goal: a reproducible Python environment in /neural (a virtual environment, ignored
by git) where PyTorch actually runs on the GPU.
Facts and cautions:
  - The machine's default Python is a very new 3.14.x and PyTorch was not
    installed. PyTorch may not yet publish wheels for the newest Python. Check what
    the current PyTorch release officially supports. If the default Python is not
    supported, obtain a supported one WITHOUT sudo (for example a user-space Python
    manager such as uv, or any equivalent user-level method). Prefer the newest
    Python that current PyTorch officially supports.
  - The GPU is an RTX 5070 laptop GPU (NVIDIA Blackwell consumer architecture, which
    needs a PyTorch build that includes support for it; as far as I know that means
    CUDA 12.8-or-newer builds). Choose the PyTorch build accordingly. If the installed
    NVIDIA driver is too old for the build you need, that is a system change:
    follow rule 2.
  - Pin versions (a requirements or lock file) so the environment can be rebuilt.
  - Do not assume a working torch.cuda.is_available() proves anything: run a real
    GPU computation (a matrix multiply and a small convolution with backward pass)
    and confirm the GPU's architecture is in the build's supported list.
  - Keep dependencies modest: PyTorch, NumPy, an image library for PNGs, a plotting
    or imaging library for the review image, and a test runner are enough. Add
    others only if clearly useful.

--------------------------------------------------------------------------------
3. THE PACKAGER
--------------------------------------------------------------------------------
Goal: convert a source dataset (a directory of episodes as produced by the engine)
into a compact, fast-to-read packed dataset at a chosen training resolution.

Requirements:
  - Input: a dataset root such as engine/data/pilot_v1/ whose splits are the
    train/val/test directories, each containing episode directories (frames/*.png
    plus a manifest). Ignore anything that is not an episode (plan, report,
    aborted log, review folders). Include only episodes marked complete in their
    manifest; read the manifest's frame list as the truth (episodes truncated by
    the engine's clipping failsafe are valid and simply shorter). Refuse, with a
    clear message, any manifest whose schemaVersion is not the one DATASET-SCHEMA.md
    describes.
  - Resolution is a parameter. Downsample from the 320x240 masters with an
    area/box filter (matching how the engine's own review images were made), and
    document the exact method. Produce 96x72 and 64x48 for the pilot (both divide
    nicely by 8 or 16 for convolutional networks). Support other sizes without code
    changes. The PNG masters stay as the source of truth; packed data is derived
    and rebuildable.
  - Output: per-frame images as uint8 RGB (confirm the PNGs' channel layout and
    convert if needed), plus per-frame labels (actionX as float with a defined
    representation for null, actionHasClicked, viewUnsafe, episode index, frame
    index), plus per-episode metadata (split, seed, truncated flag, source path,
    length). Choose the simplest format that gives fast random access and does NOT
    require loading a whole dataset into RAM (memory-mapped flat arrays plus a small
    index is one reasonable choice; decide for yourself). The pilot at 96x72 is
    under 2 GB, but the later bulk dataset could be tens of GB and the machine has
    about 30 GiB of RAM.
  - Keep the analysis columns (persona, raw click, player pose, target and
    candidate information from the debug fields, and similar) in a separate sidecar
    keyed by (episode, frame), not loaded by default.
  - Provenance: the packed dataset records the source dataset's schemaVersion,
    plan name, configHash, engineSourceHash, the packer version, the resolution, the
    downsampling method, and counts, so any packed set can be traced to the engine
    code that made it.
  - Scale and reuse: decode PNGs in parallel (24 CPU cores available); work in
    bounded memory; be deterministic (packing the same input twice gives identical
    output); and be incremental/idempotent so that adding more episodes or another
    dataset later does not force repacking what is already packed.
  - Integrity checks during packing: image size matches the manifest, frame counts
    match, no undecodable PNG, no duplicate (episode, frame). Report problems
    clearly rather than silently skipping.
  - Compute and store dataset statistics (frame and episode counts per split,
    per-channel pixel mean and standard deviation, the number and share of
    viewUnsafe frames, the share of frames with actionHasClicked false).

4. THE LOADER
--------------------------------------------------------------------------------
Goal: a PyTorch-friendly loader over a packed dataset that serves training windows
and longer clips correctly and fast.

Core primitive: a contiguous CLIP from one episode: L consecutive frames and the
labels for them. Training windows and rollout clips are both built from it.

Window semantics. A training window has K context frames and H target frames
(K and H are parameters; H defaults to 1; support larger H, as multi-step training
and rollout evaluation will want it). The ACTION ALIGNMENT RULE from the schema
governs everything: actionX[i] is the action that drives the transition from frame
i to frame i+1. So for context frames j = t-K .. t-1 and target frame t, the action
paired with frame j is actionX[j] (the action taken AFTER seeing frame j). The
loader's documentation must state this plainly, and a test must prove it (Section
6). Return each action as a small float vector: [actionX, actionHasClicked], with
actionX = 0 when no click has happened yet. Document the representation.

Validity rules:
  - A window never crosses an episode boundary, and never crosses splits.
  - Drop every window that contains ANY viewUnsafe frame (context or target). Offer
    an option to include them for analysis only. Report how many windows this removes
    at a few settings (for example K = 4, 8, 16 with H = 1 and H = 4).
  - By default only windows with a full K frames of context are valid (no padding at
    the start of an episode). Optionally allow padding by repeating the first frame.
  - The final frame of an episode (actionX null) can only ever be a target, never a
    context frame; make sure no window requires an action that does not exist.
  - The first frames after an episode start look different from mid-episode frames
    (the player starts in a start hallway); do not treat that as a problem, just do
    not exclude them unless the rules above do.

Interface needs:
  - A training dataset/loader: random windows, reproducibly seeded, uniformly over
    valid windows, with the usual PyTorch DataLoader features (workers, pinned
    memory, batching). Images returned as tensors with a documented dtype and range
    (a [-1, 1] float is a common convention for diffusion models; make it a
    parameter or helper).
  - An evaluation access path: a deterministic, ordered iteration over valid
    windows for the val and test splits, plus random access to any clip by (split,
    episode, start frame, length) for later rollout and replay evaluation.
  - Resolution is selected by which packed set you point it at.
  - Must not be the training bottleneck: it should comfortably out-run what a small
    model can consume (aim for a few thousand windows per second at 96x72 with
    K = 4 on this machine; measure and report what you get). If it is slow,
    consider keeping a split in RAM when it fits.
  - Not tied to the pilot: it should work unchanged on a future packed set that is
    10 to 20 times larger.

5. THE REVIEW IMAGE (for the user)
--------------------------------------------------------------------------------
Produce ONE image the user will look at, saved in a gitignored review folder inside
the packed-data location, as the file windows.png:
  - About 6 training windows drawn through the loader (not by reading PNGs
    directly), each shown as its K context frames followed by the target frame, with
    the action values (actionX and actionHasClicked) printed under each frame. Choose
    windows where the action changes (just after a click) so the user can see the
    turn begin one frame after the action appears. Use the 96x72 packed set,
    enlarged with nearest-neighbor so pixels are visible, and a context length of
    about 4.
  - A second group of 2 windows that were EXCLUDED because they contain a viewUnsafe
    frame, clearly labeled, with the unsafe frames marked, so the user can judge
    whether the flag matches what their own eyes call a bad frame.
When you finish, tell the user the path and say what to look for: the frames should
look like one smooth, continuous sequence; the action labels should line up with the
motion (a turn starting at or just after the frame where the action value changes);
and the excluded windows should visibly be the camera pressed against or through a
wall.

6. VERIFICATION (this is the whole list; do not add to it)
--------------------------------------------------------------------------------
 1. Environment: record Python and PyTorch versions, CUDA version, the GPU name and
    architecture, and the result of the real GPU computation of Section 2.
 2. Alignment test: using real pilot episodes, assert that for a sample of windows
    the action paired with each context frame j equals the manifest's actionX[j] (and
    equals the manifest's controlSignalX[j+1], the cross-check the schema describes),
    and that actionHasClicked matches the manifest.
 3. Rules test: no returned window contains a viewUnsafe frame, no window spans two
    episodes, no episode appears in two splits, and the number of valid windows
    equals a count computed independently directly from the manifests.
 4. Pixel round trip: for a handful of random frames, the packed pixels equal an
    independent downsample of the source PNG with the documented method.
 5. Totals: the packed pilot's frame count and viewUnsafe count match the Stage 2
    report (88,047 frames; 357 viewUnsafe frames) when counted across all splits.
    If they do not, find out why and report it (this is a check-in trigger if it
    affects labels).
 6. Determinism and reuse: pack the pilot twice (compare content hashes), and
    confirm that re-running skips work already done.
 7. Throughput and smoke test: measure loader throughput (windows per second at
    96x72, K = 4, with a sensible number of workers), then run a few dozen training
    steps of a trivial network (for example a tiny convolutional net) fed by the
    loader on the GPU, to prove the whole path works. Do not train a real model.
Everything visual is judged by the user. Not requested, so do not do them: further
benchmarks, exhaustive property tests, extra visual checks, training a real model.
